# Where tidymove came from

**Evidence class: author-reported background.** The author describes a real migration spread across nine calendar days, with AI agents helping to inventory, ask questions, plan, copy, check, and record the outcome. Private source records are not distributed with this kit, so readers cannot independently verify that account here.

This public summary deliberately omits device configurations, organizations, accounts, locations, exact counts, file sizes, and detailed personal timelines. It is context for the process, not a benchmark, product test, or recommended layout.

## The useful lessons

- A folder name is not enough to decide what it contains or who owns it. Ask short questions with enough context to answer.
- Work continues during a long migration. Compare current copies again after a pause.
- An inventory can miss files even when its command succeeds. Record unreadable locations and give every item an explicit outcome.
- Protecting an old drive is a step to verify, not a setting to assume.
- Copying successfully is different from proving equal contents, opening the result, and recovering from a backup.
- App data and agent history need their own plans. A folder copy alone does not rebuild a working setup.
- Keep decisions, failures, corrections, and unfinished work together so another session can continue.

## What this does not establish

The original experience does not prove that the packaged scripts work on every computer. The Windows smoke test uses synthetic files and simulated disk states. macOS and Linux recipes remain untested on their target platforms.

Nine days included pauses, owner decisions, and repeated checks. It is not a measure of total labor or transfer speed. Estimate each new run from its own data, storage health, verification work, and availability for decisions.

The [pitfall catalog](pitfalls.md) turns the lessons into review questions. Treat each as something to test in the current run; do not assume a historical fix proves a new setup safe.
